    **Step 3 — Create scoring_service.py:**
    Implement the scoring pipeline module at backend/app/services/scoring_service.py. Required functions:

    3a. `parse_score_points(score_points_text: str) -> list[dict]`
    Parse the multi-level numbered outline format observed in questions.json into a flat list of individual scoring point dicts.
    Each dict: `{"id": int, "section": str, "text": str}`
    - Top-level markers: `r'(?:^|\n)\s*(\d+|[lI])\s*[、.]\s*(.+?)(?=\n\s*\d+\s*[、.]|\n\s*\(\d+\)|\Z)'` — normalize OCR artifacts `l` and `I` to `1`
    - Sub-point markers: `r'\(\d+\)\s*(.+?)(?=\n|$|\(\d+\))'` — extract parenthesized sub-items
    - Each leaf-level entry gets: incremental `id`, `section` (top-level heading text), and `text` (the sub-point content, or heading if no sub-points)
    - Return empty list if no points parsed
    - Log a warning if parsed count is 0 or unexpectedly small (< 2)

    3b. `build_scoring_prompt(question_text: str, points: list[dict], transcript: str) -> str`
    Construct the user prompt for LLM scoring. Format:
    - Question text (full)
    - Candidate answer (ASR transcript)
    - Numbered list of scoring points with section context
    - Output instructions: for each point, return COVER/PARTIAL/MISS verdict, evidence from transcript, reasoning
    - Include instruction: ignore ASR homophone errors (同音错别字), judge by semantic meaning

    3c. `SCORING_SYSTEM_PROMPT` (module-level constant)
    System prompt instructing Qwen to act as expert evaluator for civil service exam interview answers. Key instructions per RESEARCH.md Pattern 4:
    - Role: expert evaluator for civil service exam interview answers
    - Task: compare candidate's spoken answer against scoring criteria
    - Output: valid JSON only
    - ASR tolerance: do NOT penalize transcription errors (homophones, similar sounds)
    - Evaluate semantic meaning, not exact wording
    - Chain-of-thought: require evidence before verdict
    - Definitions: COVER = semantic meaning fully matches; PARTIAL = partially addresses, key elements missing; MISS = not addressed or semantically unrelated

    3d. `evaluate_answer(session_id: str, question_index: int, question: dict, retry_count: int = 0) -> dict`
    Full scoring pipeline (per D-01, D-02, D-03, D-04, D-10):
    1. Load WebM recording from `recordings/{session_id}/q{question_index}.webm` — raise FileNotFoundError if absent
    2. Convert WebM to WAV via `/tmp/ffmpeg` static binary (same flags as RESEARCH.md Pattern 2: `-y -i {in} -ar 16000 -ac 1 -sample_fmt s16 {out}`)
    3. Validate WAV: file_size > 44 bytes (header-only = silent/empty); if empty, return status "failed" with "无有效语音" message
    4. Call `transcribe_audio(wav_path)` from asr_service — if empty transcript, return status "failed" with "语音识别无结果"
    5. Parse scorePoints: `points = parse_score_points(question["scorePoints"] or "")` — if no points parsable, treat entire scorePoints text as single criterion
    6. Build system + user prompts using SCORING_SYSTEM_PROMPT and build_scoring_prompt()
    7. Call DashScope Generation API: `dashscope.Generation.call(model="qwen-max", messages=[...], result_format="message", temperature=0.1, top_p=0.8, seed=42)`
    8. Parse response: `json.loads(response.output.choices[0].message.content)` — if json.loads fails, treat as LLM failure
    9. Validate result JSON structure — must have "coverage" array with id/verdict/evidence/reasoning per point, and "feedback" string
    10. Compute coverage summary: coveredCount = count of COVER verdicts, totalCount = total points
    11. If any step fails (FileNotFoundError, ffmpeg error, ASR error, LLM error, JSON parse error):
        - If retry_count == 0: retry once (retry_count=1, recursive call)
        - If retry_count >= 1: return status "failed" with error message
    12. On success: return dict with status "scored", transcript, coverage array, feedback, coveredCount, totalCount
    - On failure: return dict with status "failed" and error message string

    3e. `save_scoring_result(session_id: str, question_index: int, result: dict) -> None`
    - Load existing scoring.json from `recordings/{session_id}/scoring.json` (or empty list if absent)
    - Upsert: replace entry with matching question_index, or append if new
    - Write back to scoring.json with `json.dump(..., ensure_ascii=False, indent=2)`

    3f. `load_scoring_results(session_id: str) -> list[dict]`
    - Read scoring.json from `recordings/{session_id}/scoring.json`
    - Return list of result dicts (empty list if file absent)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → POST /api/scoring/evaluate | Untrusted input crosses here: session_id, question_index, question_id from frontend |
| Client → POST /api/scoring/rescore | Same as evaluate; also rate-limit boundary |
| LLM output → scoring.json | LLM-generated JSON is parsed and validated before persisting |
| LLM output → client (via GET /results) | LLM feedback text rendered in browser; React escaping as defense |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | scoring endpoints (session_id path) | mitigate | Validate session_id against `^[a-f0-9-]+$` before any filesystem access; use pathlib to prevent traversal |
| T-04-02 | Tampering | scoring_service (LLM prompt) | mitigate | ASR transcript is system-generated, not user input. Use system/user role separation in dashscope messages format. Transcript placed in user message as data, not instructions. |
| T-04-03 | Tampering | scoring_service (LLM output) | mitigate | Validate JSON structure after `json.loads()` — check coverage array and feedback key exist before saving. If validation fails, treat as LLM failure (retry once, then degrade). Never pass raw LLM output as-is. |
| T-04-04 | Denial of Service | scoring router (rescore endpoint) | mitigate | In-memory rate limit: max 3 re-scores per question per session. Returns HTTP 429 on 4th attempt. Dict reset on server restart (acceptable for v1). |
| T-04-05 | Information Disclosure | scoring endpoints (error messages) | mitigate | Return generic error details to client. Full error details logged server-side only. Never include stack traces or file paths in HTTP responses. |
| T-04-06 | Denial of Service | scoring router (evaluate endpoint) | accept | No rate limit on initial scoring triggers (per-question, max 4 per session). DashScope API has its own rate limits. Low risk for v1 single-user. |
</threat_model>
